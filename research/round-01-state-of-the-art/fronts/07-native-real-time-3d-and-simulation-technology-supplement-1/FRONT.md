### 7. Native Real-Time 3D & Simulation Technology [Supplement 1]

**Graphics abstraction layers — the AGPL-safe shortlist:**

| Item | What it gives us | License verdict for AGPL use | URL |
|---|---|---|---|
| **wgpu** (gfx-rs, Rust) | WebGPU-API-as-native-library: one safe API over **Vulkan, Metal, D3D12, OpenGL**, plus wasm/WebGPU from the same code. Core of Firefox/Servo/Deno WebGPU. C API via wgpu-native (`webgpu.h`) for non-Rust hosts | **MIT OR Apache-2.0. YES — recommended default** if the team can work in/around Rust; one codebase serves native flagship *and* browser tier | https://github.com/gfx-rs/wgpu |
| **Dawn** (Google, C++) | The other `webgpu.h` implementation (Chromium's): native WebGPU on D3D12/Metal/Vulkan/OpenGL, Tint shader compiler, client-server “Wire” for sandboxed processes | **BSD-3-Clause. YES** — the natural choice for a C++ flagship that wants the WebGPU programming model natively | https://dawn.googlesource.com/dawn/+/43b805ec9edc136b42b55f77ff46f90e73ca2a07 |
| **bgfx** (bkaradzic, C++) | Battle-tested “bring your own engine” renderer: D3D11/12, Metal, Vulkan, OpenGL/ES, WebGL backends; renderer only (no scene/physics) | **BSD-2-Clause. YES** — lowest-risk C++ renderer abstraction; pair with your own scene graph (or VTK) | https://bkaradzic.github.io/bgfx/overview.html |
| **The Forge** (ConfettiFX / The Forge Interactive) | Higher-level cross-platform framework (rendering, resource loading, animation, ray-tracing examples) on DX12/Vulkan/Metal; Quest support | **Apache-2.0 for PC/macOS/iOS/Android/Steam Deck/Quest in the public repo; consoles are a separate commercial licence.** YES for desktop/mobile targets; do not assume console rights | https://github.com/ConfettiFX/The-Forge |
| **Diligent Engine** | Low-level C++ graphics library (GL/GLES, D3D11/12, Vulkan) | **Apache-2.0. YES** — credible bgfx alternative | (via https://www.awesomelist.link/lists/awesome-vulkan/) |
| **Raw Vulkan + Metal (via MoltenVK or native)** | Maximum control/perf; MoltenVK provides Vulkan-on-Metal for macOS | Vulkan headers/SDK are Khronos open (Apache/MIT components); **MoltenVK is Apache-2.0. YES**, at the highest engineering cost of any option here | (standard — not pinned this pass) |
| **Godot 4** | The only *complete* game engine (editor, scene system, Vulkan Forward+/Mobile + GLES3 compatibility renderers, physics, OpenXR support) that is truly open source | **MIT. YES — the only engine on this list you may fork, modify and redistribute inside an AGPL product.** Caveats: its built-in physics is game-grade, not tissue-grade (drive SOFA/PhysX via GDExtension); volume rendering must be custom/VTK sidecar | https://docs.godotengine.org/en/4.2/about/faq.html |
| **Unreal Engine 5** (Epic) | What many commercial sims are built with; source-available, Nanite/ Chaos physics | **NO for an AGPL product.** Proprietary EULA, **5% royalty on gross revenue over $1M lifetime per product** (seat licences for non-game commercial use over $1M), engine modifications remain Epic's IP, **no right to redistribute the engine under AGPL**. Using it makes the product not-open-source by construction | https://www.unrealengine.com/uses/switching-to-unreal-engine ; analysis: https://blog.promise.legal/game-engine-license-agreements-unreal-unity-godot/ |
| **Unity** | The other incumbent in commercial medical VR (incl. iMSTK's Unity asset) | **NO for an AGPL product.** Proprietary per-seat subscription by revenue tier (Personal capped at $200k total finances; runtime fee proposed 2023, cancelled Sept 2024). Engine cannot be redistributed or open-sourced; plan terms have changed unilaterally before — a structural risk for a “definitive” OSS platform | https://umatechnology.org/game-engine-licensing-explained-unity-runtime-fees-unreal-royalties-and-godots-model-in-2026/ |

**GPU volume rendering & tissue simulation at interactive rates:**

| Item | What it gives us | License verdict | URL |
|---|---|---|---|
| **VTK GPU volume ray-casting** (`vtkGPUVolumeRayCastMapper` / SmartVolumeMapper) | Production volume rendering, transfer functions, multi-volume, clipping — the renderer inside Slicer/ParaView | **BSD-3. YES** (see Front 9) | https://sources.debian.org/src/paraview/5.13.2%2Bdfsg-3/VTK/Documentation/docs/about.md/ |
| **SOFA FEM** (§2, Front 9) | Corotational/nonlinear FEM, implicit solvers, CUDA components, cutting via topology change — highest physical fidelity available open | **LGPL core. YES as libraries** | https://www.sofa-framework.org/about/features/ |
| **PhysX 5** (NVIDIA) | Rigid + cloth + **FEM soft bodies + PBD particles/fluids**, SDF collision; GPU path is CUDA. GPU simulation source was fully open-sourced in the 5.6 release (Apr 2025, 500+ CUDA kernels) | **BSD-3-Clause. YES — code is clean; the trap is hardware, not licence:** GPU acceleration requires an NVIDIA CUDA GPU, so AMD/Apple-Silicon machines fall back to CPU. Never make CUDA the only path | https://www.cgchannel.com/2025/04/nvidia-open-sources-physxs-gpu-simulation-code/ ; https://developer.nvidia.com/physx-sdk |
| **PositionBasedDynamics / XPBD research code** (Interactive Graphics & Simulation Group, Innsbruck; Macklin et al.) | Reference XPBD implementation: FEM, cloth, rigid coupling with compliance-based (physical-unit) constraints | **MIT. YES** — the right seed for a custom, portable XPBD tissue solver (CPU + your own GPU compute) if SOFA/PhysX don't fit | (cited in §2 audit context; repo: https://github.com/InteractiveComputerGraphics/PositionBasedDynamics — verify licence file at pin time) |
| **NVIDIA Newton / Warp, Isaac Sim, Omniverse** | GPU-native differentiable physics (Newton, co-developed with DeepMind/Disney, Linux Foundation) and the robotics-sim platform most surgical-robotics RL papers now use | **Newton: Apache-2.0 (YES). Warp: Apache-2.0 with NVIDIA terms to check. Isaac Sim / Omniverse: proprietary platform licences (NO as a redistributable base)** — use Newton/Warp as libraries, not Omniverse as your shell | https://developer.nvidia.com/physx-sdk (Newton note) |

**What the leading surgical simulators actually run on (honest picture):** mostly **Unity or Unreal + a proprietary physics/haptics layer + vendor hardware** (Surgical Science, FundamentalVR, Osso VR, PrecisionOS are Unity/Unreal-class products; Intuitive's SimNow runs on the da Vinci console itself). Academic/open systems run on **SOFA, iMSTK, or Slicer/VTK** (Front 9). There is no commercial incumbent built on an open engine — which is precisely the gap an AGPL native flagship can occupy, and also a warning: the incumbents buy their polish with engine ecosystems (asset stores, XR plugins) that Godot/wgpu do not match.
